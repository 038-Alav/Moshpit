# Architecture Baseline

```text
Web / future clients
   | HTTP commands / snapshots
   v
Fastify modular monolith -------------------------- PostgreSQL
   |                                                source of truth
   | transactional outbox dispatcher
   v
RealtimePublisher port
   |
   v
Centrifugo
   |
   | authorized WebSocket subscriptions / events
   v
Connected clients
```

## Domain module ownership

- `identity`: guest/account identity and authenticated session boundary.
- `setlists`: persistent Setlist aggregate, SetlistItems and ownership; D1 is owner-only, with collaborator authorization deferred to D5.
- `pits`: Pit lifecycle, membership, Pit roles and Pit-specific policy.
- `live-sets`: LiveSet aggregate, LiveSetItems and collaborative commands.
- `playback`: PlaybackSession and PlaybackEndpoint contracts/coordinator.
- `music-catalog` (later phase): CanonicalTrack, ProviderMapping, search, matching and provider adapters.
- `realtime`: event envelope, outbox dispatch port and Centrifugo adapter.
- `shared`: cross-cutting technical infrastructure only; no business rules.

Modules communicate through application interfaces and explicit contracts. Domain modules do not mutate each other's repositories directly. A Pit is the social/session context; a Live Set is its independent active music selection; a PlaybackSession tracks shared playback state for that Pit/Live Set.

## Ownership and consistency

- Fastify owns domain logic, authorization, commands and state transitions.
- PostgreSQL is the source of truth for identities, Setlists, Pits, Live Sets, PlaybackSessions, PlaybackEndpoint reports and outbox records.
- State-changing commands enter through HTTP.
- Domain writes and outbox records are committed in one transaction.
- Events are published only after commit through `RealtimePublisher` to Centrifugo.
- Clients cannot publish authoritative Pit events directly.
- Clients recover through HTTP snapshots and aggregate revisions; Centrifugo is not the source of truth.

## Music catalog scale

Moshpit does not mirror entire provider catalogs. Provider adapters perform federated/on-demand search. PostgreSQL stores Moshpit-owned Setlists/Live Sets and only canonical track records/mappings referenced by selected items, plus bounded provider-specific cache where permitted. Device-local libraries are optional import sources in a later phase, not the default source of truth or a participation requirement.

## Runtime and packaging independence

- Fastify is a Node.js process and can run natively on Windows or Linux.
- PostgreSQL and Centrifugo can run as native services/binaries or containers.
- Docker/Podman are optional packaging/orchestration tools, not product dependencies.

## D1 implementation notes

- Guest session bearer tokens are generated by the identity module; only SHA-256 hashes are stored in PostgreSQL.
- Fastify issues Centrifugo connection JWTs and channel-scoped subscription JWTs. A Pit subscription token is issued only to a current Pit member.
- PostgreSQL migrations are versioned SQL files in `apps/api/migrations`; `schema_migrations` tracks applied files.
- Idempotency records are scoped by identity and `Idempotency-Key`; request hashes prevent key reuse with a different command.
- Outbox rows have leases and retry/backoff fields. Duplicate publication remains possible across a crash boundary, so event consumers deduplicate by `eventId`.
- Setlist item and Live Set item positions are aggregate-local dense integers. D1 reorder commands send the complete ordered item ID list and require the observed aggregate revision.
